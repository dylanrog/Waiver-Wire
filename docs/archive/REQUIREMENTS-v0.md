# Fantasy Football Waiver Wire Agent — Requirements

## 1. Product Goal

Build a web application that connects to a user's **Sleeper fantasy football league** and acts as a personalized fantasy football assistant.

The application should answer:

> **"What moves should I make this week to improve my fantasy team?"**

The application should analyze the user's actual roster and waiver wire rather than providing generic fantasy football advice.

It should eventually monitor:

* Waiver-wire players
* Injuries
* Depth-chart changes
* Player usage
* Expert rankings
* Upcoming schedules
* Kicker matchups
* Defense matchups

and turn those signals into personalized recommendations.

# 5. Team Analyzer

Create a team-analysis service.

It should identify positional strength for:

* QB
* RB
* WR
* TE
* K
* DST

Determine:

* Starter quality
* Bench depth
* Number of viable starters
* Injury risk
* Bye-week concerns
* Potential upgrade opportunities

Example:

```text
RB: 6.5/10
WR: 8.7/10
TE: 7.9/10
K: 5.1/10
DST: 4.2/10
```

These scores should be based on data, not simply generated by the LLM.

# 6. Waiver-Wire Analyzer

Retrieve available players from Sleeper.

Do **not** send every available player to the LLM.

First perform deterministic filtering.

Potential candidate criteria:

* Position
* Recent production
* Snap share
* Touches
* Targets
* Target share
* Routes
* Red-zone usage
* Recent trend
* Injury status
* Depth-chart position
* Roster percentage
* Upcoming schedule

The application should reduce the waiver pool to a manageable candidate set.

Example:

```text
400 available players
        ↓
Statistical filtering
        ↓
50 candidates
        ↓
Team-specific filtering
        ↓
15 candidates
        ↓
LLM analysis
        ↓
Top 5 recommendations
```

# 7. Personalized Waiver Ranking

Waiver rankings should be based on **the user's roster**, not just player talent.

The system should consider:

```text
Player value
+
User positional need
+
Expected opportunity
+
Upcoming schedule
+
Injury situation
+
Long-term value
+
Player availability
+
Drop cost
```

Example:

> Player A is a better overall fantasy player than Player B, but Player B is the better waiver pickup for this particular team because the user has strong WR depth and weak RB depth.

# 8. "Next Man Up" System

This should be a major feature.

Detect situations such as:

```text
RB1 injured
      ↓
Identify team
      ↓
Identify replacement candidates
      ↓
Determine expected workload
      ↓
Check waiver availability
      ↓
Evaluate fantasy impact
```

The system should look for:

* Season-ending injuries
* IR placements
* Multi-week injuries
* Suspensions
* Depth-chart promotions
* Trades
* Starting-role changes
* Coaches announcing changes in usage

Example recommendation:

> 🚨 **Priority Waiver Target**
>
> Player X is available in your league.
>
> The team's starting RB is expected to miss significant time. Player X is currently the primary backup and is projected to receive the majority of the additional workload.

---

# 9. Opportunity Change Detection

Don't only look at injuries.

Detect players whose opportunity is changing.

Potential signals:

* Snap share increasing
* Carries increasing
* Targets increasing
* Route participation increasing
* Red-zone usage increasing
* Starting lineup promotion
* Another player's injury
* Trade of a competing player
* Coaching announcement

Example:

```text
Week 1:
Snap share: 32%

Week 2:
Snap share: 58%

Week 3:
Snap share: 74%
```

This should trigger:

> **Rising Opportunity**

# 10. Kicker Streaming

Create a dedicated kicker analysis module.

For the upcoming week, collect rankings/projections from several reputable fantasy sources.

Normalize their rankings into a common format.

Example:

```text
Player       Source A   Source B   Source C   Consensus
Kicker A        4          7          5          5.3
Kicker B        8          3          6          5.7
Kicker C        11         9          7          9.0
```

Consider:

* Expert rankings
* Projected points
* Team scoring environment
* Opponent
* Vegas implied points where available
* Home/away
* Weather
* Wind
* Field-goal opportunity

Then compare available kickers against the user's current kicker.

The system should answer:

> **Should I keep my kicker or stream someone else?**

It should also look ahead multiple weeks.

---

# 11. Defense Streaming

Build an equivalent DST module.

Consider:

* Expert rankings
* Opponent offense
* Opposing QB
* Sack potential
* Turnover potential
* Vegas implied score
* Home/away
* Weather
* Offensive injuries
* Upcoming schedule

The system should evaluate:

```text
Current DST
vs
Best available DST this week
vs
Best available DST over next 2–4 weeks
```

This enables recommendations such as:

> Drop your current DST and add Denver.

or:

> Keep your current DST this week, but add Chicago for Week 3.

---

# 12. Schedule Analysis

Create a schedule-ranking system.

For each relevant player/team, calculate upcoming matchup difficulty.

At minimum:

* Current week
* Next week
* Next 3 weeks
* Next 4 weeks

This is especially important for:

* DST
* K
* RB
* TE

The application should distinguish between:

**Best player**

and

**Best player for the upcoming schedule.**

# 13. Recommendation Engine

Create a centralized recommendation engine.

It should generate recommendations such as:

### ADD

Player should be added.

### HOLD

Player should remain on the roster.

### DROP

Player is a reasonable roster cut.

### STREAM

Temporary pickup for favorable matchup.

### MONITOR

Interesting player but not worth adding yet.

### PRIORITY ADD

Urgent waiver opportunity.

---

# 14. Recommendation Structure

Recommendations should be structured data.

Example:

```json
{
  "action": "ADD",
  "player_id": "123",
  "priority": 9.2,
  "confidence": "HIGH",
  "suggested_drop": "456",
  "faab_min": 12,
  "faab_max": 18,
  "time_horizon": "4 weeks",
  "reasons": [
    "Starting RB is injured",
    "Expected workload has increased",
    "Player is available on waiver wire",
    "User has weak RB depth"
  ],
  "risks": [
    "Potential committee"
  ]
}
```

The frontend should render this structured data rather than displaying raw LLM output.

# 15. AI Layer

Use the LLM primarily for:

* Reasoning
* Interpreting news
* Synthesizing multiple sources
* Comparing candidates
* Explaining recommendations
* Identifying uncertainty

Do **not** rely on the LLM for basic calculations that can be performed deterministically.

Architecture:

```text
Raw Data
   ↓
Data Processing
   ↓
Candidate Selection
   ↓
LLM
   ↓
Structured Recommendation
   ↓
Recommendation Engine
   ↓
Frontend
```

---

# 16. Model Strategy

Design the application so the LLM provider is configurable.

Do not hard-code Claude.

Support a provider abstraction such as:

```text
LLMProvider
├── Anthropic
├── DeepSeek
└── Future providers
```

Initially, use a **cheap model for high-volume analysis**.

Reserve a more capable model for complex final decisions.

Potential architecture:

```text
Simple extraction
       ↓
Cheap model

Candidate analysis
       ↓
Cheap model

Final roster decision
       ↓
Stronger model
```

# 17. Source Attribution

Every recommendation should be traceable.

For example:

> **Why?**

* Starting RB placed on IR
* Backup moved to starting role
* Expert rankings moved player from #48 → #24
* Snap share increased
* Player is available in your league

The UI should allow the user to see the underlying sources.

AI recommendations should never present unsupported claims as facts.

# 25. Evaluation System

Create an evaluation framework for the AI recommendation system.

Create test cases such as:

> RB1 is injured → RB2 is available → system should identify RB2.

> User has three strong WRs → system shouldn't recommend adding another marginal WR over a strong RB.

> Current DST has terrible matchup → available DST has strong matchup → system should recommend streaming.

> Kicker has favorable matchup → system shouldn't recommend unnecessary change.

Track:

* Recommendation accuracy
* False positives
* False negatives
* Citation/source accuracy
* Data freshness
* LLM cost
* Latency
* Recommendation confidence

Eventually compare:

**DeepSeek vs Claude**

on identical fantasy football scenarios.

# 29. Core Architectural Principle

> **The application must separate data retrieval, deterministic analysis, AI reasoning, and presentation.**

The LLM should **never be treated as the source of truth for structured fantasy football data**.

AI recommendations must be based on retrieved and traceable data.

Recommendations should be returned as structured objects rather than free-form text.

The application should be able to explain **which data and sources caused a recommendation to be made.**

---

# 30. Product Philosophy

The application is **not** intended to answer:

> "Who are the best fantasy football players?"

It is intended to answer:

> **"Given my exact team, league, waiver wire, injuries, player opportunities, upcoming schedule, and available streaming options, what should I do right now?"**

The application should prioritize **actionable, personalized recommendations over generic rankings.**
